Act 4 · Where this goes

The bottleneck moved.

The constraint used to be whether something could be built at all. It is now deciding what is worth building, and what an agent should be allowed to reach.

The pattern

Build a thing. Replace a workflow. Run the system.

The three tools differ mainly in how much access they need, and access is what organizations are least prepared to grant.

Slides™ · Produces an output

The agent produces an artifact and touches nothing else. There is no access to grant and nothing to approve. Most organizations are already here.

Mæla™ · Replaces a workflow

The agent replaces a pipeline that used to involve people, vendors and several weeks. Many organizations are already here without having decided to be.

BankMCP™ · Operates a system

The agent operates on real data inside a running system. This is where most organizations have no policy at all.

Who builds

Three roles, one job.

Desirability, feasibility and viability have been drawn this way for twenty years, on the assumption that covering all three took three people. That assumption no longer holds.

Desirability
The designer used to hand over a file and hope. Now they build the real thing and fix it because it felt wrong.
Feasibility
The engineer used to build what the spec said. Now they shape the problem and ship the whole slice.
Viability
The PM used to write the requirement and wait. Now they turn up with a working version.

Organise teams around problems,
not around disciplines.

What enterprises have to rethink

The remaining constraints are organizational.

None of these are AI problems. Each is a decision an organization has to make before any of this becomes useful.

01 · Access is the constraint

Once an agent can operate a system, the only question that matters is what it is allowed to reach. Organizations should decide this before granting access, and enforce it outside the model rather than in a prompt.

02 · Work is smaller than procurement

Work that once needed a project now takes an afternoon, while budgeting and approval are still sized for projects. Organizations should create a route for work too small to justify a business case.

03 · Headcount is not capacity

Output no longer follows the org chart. Planning that starts from team size will consistently misjudge what is achievable.

04 · The org chart assumes handoffs

Titles and team boundaries still assume work passes between disciplines. Organizations should let the people closest to a problem build for it directly.

AI that writes software is settled.
What comes next is AI that operates it.
